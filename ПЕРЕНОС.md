# Перенос «Раппорт: ЖиваЯ» на Timeweb

## Статус

Подготовлены отдельная команда сборки для Timeweb, серверный запуск и `.env.example` без секретов. Репозитории, другой сайт, домены и рабочие сервисы не изменены.

**Полный перенос ещё не готов к выпуску.** Подключение GitHub не подтверждено, приложение Timeweb не создано. Сначала нужно решить перечисленные ниже зависимости ИИ, Telegram, привилегированных действий и медиа.

## 1. GitHub без перезаписи другого сайта

На компьютере в Lovable: название проекта → Settings → Git. На телефоне: режим Chat → меню `…` → Settings → Git.

1. Если соединение уже есть, проверьте репозиторий и выбранную ветку. Не отключайте его только ради проверки: повторное подключение создаёт новый репозиторий.
2. Если соединения нет, подтвердите создание отдельного репозитория, затем подключите GitHub и разрешите доступ Lovable. **Git sync создаёт новый приватный репозиторий, а не подключает существующий.** Другой сайт оставьте нетронутым.
3. Двусторонняя синхронизация работает с одной выбранной веткой. Для Timeweb используйте ту же ветку; изменения других веток сначала объединяйте с ней.
4. В GitHub проверьте `src/`, `public/`, `package.json`, `bun.lock`, `vite.config.ts`, `.env.example`, `drizzle/migrations/` и исходные настройки. Не должно быть реального `.env`, секретов, `node_modules` и результатов сборки.
5. **Текущий `.gitignore` не содержит исключения `.env`.** Lovable запретил его редактирование агенту: файл управляется платформой. На вашей стороне перед экспортом обеспечьте исключение `.env` и `.env.*` с исключением для `!.env.example`. Если `.env` уже отслеживался, одного нового правила недостаточно: проверьте историю и удалите его из отслеживания; при обнаружении секретов замените их. Не редактируйте автоматически созданные настройки Cloud.
6. Если изменения сделаны в черновике Lovable, примите его в основной проект перед проверкой синхронизации.

Агент не может видеть настройки Git sync, авторизовать GitHub или подтвердить передачу файлов из этого окружения. Репозиторий в этой проверке не выбран и не изменён.

Источник: [Git sync Lovable](https://docs.lovable.dev/integrations/git-sync-overview).

## 2. Выбранный вариант: App Platform, серверное приложение Node.js

App Platform автоматически получает код из GitHub, собирает приложение, запускает сервер и обслуживает HTTPS. VPS даёт больше контроля, но требует самостоятельно обслуживать Linux, процессы, прокси и сертификаты. Для этой инструкции выбран App Platform.

**Это TanStack Start, не статический Vite-сайт и не Next.js.** Диалоги и уведомления требуют сервера. Публикации только `dist` или запуска `vite preview` недостаточно.

На внешнем сервере используйте:

```sh
npm install --include=dev
npm run build:timeweb
npm start
```

Нужен Node.js **22.12 или новее**. В проекте есть `bun.lock`, но нет `package-lock.json`, поэтому здесь не используется `npm ci`. Для проверок — `npm test`.

Внешняя сборка создаёт `.output`, включая `.output/server/` и `.output/public/`. `npm start` запускает `.output/server/index.mjs`. Обычная команда `build` сохранена для Lovable; `build:timeweb` выбирает отдельный режим Node. В окружении Lovable целевой формат принудительно остаётся управляемым: сборку именно для Node необходимо подтвердить на Timeweb.

Источник: [внешнее размещение Lovable](https://docs.lovable.dev/tips-tricks/external-deployment-hosting).

## 3. Зависимости, которые нельзя перенести простым копированием

### Данные и вход

Приложение уже имеет аккаунты, облачный прогресс, роли, баллы и истории. Старое описание «нет базы и входов» больше не соответствует проекту.

Для сохранения текущей Cloud нужны открытые значения `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID` до сборки, а на сервере — `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`. Названия сохранены для совместимости с кодом. Возьмите реальные открытые настройки проекта; локальный серверный адрес окружения Lovable нельзя использовать снаружи.

ИИ-проверка доступа, Telegram и часть операций администратора используют привилегированный Cloud-клиент. Его `SUPABASE_SERVICE_ROLE_KEY` недоступен для экспорта из Lovable Cloud. Не нужно искать этот ключ, подставлять выдуманное значение или заменять его открытым ключом. Нужен отдельно согласованный перенос этих операций или миграция сервисов; защита доступа в этой задаче не ослаблена.

Предоставленный адрес назначения — `https://zhivaya.rapportgame.ru`. Добавьте его в разрешённые адреса возврата входа: Lovable → More → Users → Auth settings (на телефоне через режим Chat → `…` → More). Проверьте почтовые ссылки и Google на новом адресе. Вход по ссылке не заменён паролями, подтверждение почты не отключено. Работоспособность входа на Timeweb и изменение разрешённых адресов пока не подтверждены.

### ИИ, Telegram и расписания

Диалоги и итоги переключены на DeepSeek (`deepseek/deepseek-flash`) через подключённый Timeweb AI Gateway. Адрес провайдера: `https://api.timeweb.ai/v1`; в Lovable запросы идут через защищённое соединение. `UDC_TIMEWEB_AI_GATEWAY_API_KEY` — ключ соединения Lovable, а не оригинальный ключ Timeweb. Его нельзя подставлять вместо ключа провайдера при внешнем запуске. `LOVABLE_API_KEY` управляется платформой и не выдаётся для ручной настройки. Внешний запуск диалогов всё ещё требует переноса проверки доступа к ИИ и отдельно настроенного серверного подключения, не простого копирования переменных.

Telegram пока использует подключённый сервис Lovable. `TELEGRAM_API_KEY_1` — ключ соединения, а не токен BotFather. `TELEGRAM_BOT_TOKEN` сохранён в секретах проекта, но текущие обработчики ещё не переключены на него. Секреты проекта не переносятся в Timeweb автоматически.

Уведомления и приглашения ещё содержат адрес рабочего сайта Lovable. Перед окончательным переключением их нужно обновить на подтверждённый адрес назначения. Telegram webhook и ежедневные задания нужно переносить согласованно: не переключайте работающего бота заранее и не запускайте два расписания одновременно.

В проекте нет `supabase/functions/`: серверные функции и входящие запросы находятся в `src/`, развёртывание Edge Functions не требуется. SQL-миграции лежат в `drizzle/migrations/`; Git sync не применяет их к другой базе автоматически. При сохранении текущей Cloud повторно применять их не нужно.

### Обложки и ролик

Медиа подключены через `*.asset.json` с адресами `/__l5e/assets-v1/`. Новый сервер не обслуживает этот путь автоматически. До выпуска нужно настроить доставку **всех** используемых обложек, оттенков и видео на внешнем адресе или согласовать перенос медиа. Указатели — не сами файлы. Пока это не выполнено.

Шрифты загружаются с Google Fonts; отдельно проверьте доступность из выбранного региона и с телефонов участниц.

## 4. Создание приложения Timeweb

Сначала решите зависимости раздела 3. До этого допустим технический пробный запуск, но не переключение участниц.

1. В Timeweb Cloud откройте **App Platform → Создать / Добавить**.
2. Выберите GitHub, авторизуйтесь и разрешите доступ только к репозиторию этого проекта. Выберите подтверждённую синхронизируемую ветку.
3. Выберите **серверное приложение Node.js**, не статический сайт; исправьте автоопределение, если оно ошиблось.
4. Оставьте **«Сборка по последнему выполненному коммиту»** включённой для автодеплоя.
5. Выберите регион и тариф; до выпуска проверьте доступность нужных сервисов из этого региона.
6. Откройте расширенные настройки:

| Поле | Значение |
| --- | --- |
| Node.js | 22.12+ |
| Корень проекта | корень репозитория |
| Установка | `npm install --include=dev` |
| Сборка | `npm run build:timeweb` |
| Запуск | `npm start` |
| Результат сборки | `.output` целиком, если поле требуется |
| Точка входа | `.output/server/index.mjs`, если поле требуется |
| Адрес прослушивания | `0.0.0.0` |
| Порт | `3000` или назначенный Timeweb порт, согласовать с `PORT` |
| Проверка состояния | `/` |

Названия полей зависят от режима Timeweb. Если отдельного поля установки нет, команда сборки: `npm install --include=dev && npm run build:timeweb`. Не меняйте рабочий каталог запуска на `.output`: `npm start` берётся из `package.json` в корне.

7. В **Расширенные настройки → Переменные → Добавить** внесите согласованные значения из `.env.example`. `VITE_*` доступны при сборке и видны в браузере, секреты — только на сервере без `VITE_`. Для существующего приложения: **Настройки → Настройка деплоя → Редактировать → Переменные**. Не помещайте секреты в GitHub или чат.
8. Создайте приложение. Проверьте журнал сборки и запуска: появился `.output/server/index.mjs`, запущен Node-сервер. Технический домен Timeweb получает HTTPS автоматически.

Источники: [серверные приложения](https://timeweb.cloud/docs/apps/deploying-backend-applications), [переменные](https://timeweb.cloud/docs/apps/variables), [работа App Platform](https://timeweb.cloud/docs/apps/how-it-works).

## 5. Домен и SSL — после проверки

App Platform → приложение → **Настройки → Домены → Редактировать**. Выберите домен Timeweb или «Внешний домен». Для внешнего домена добавьте указанную панелью A-запись у регистратора и дождитесь обновления DNS. Timeweb выпускает и продлевает Let's Encrypt автоматически.

**Не меняйте записи домена другого сайта:** привязка может автоматически обновить A-запись и переключить посетителей. До успешной проверки используйте технический домен или отдельный согласованный поддомен.

Источник: [домен и сертификат](https://timeweb.cloud/docs/apps/domain).

## 6. Проверка после запуска

Пришлите HTTPS-адрес Timeweb, подтверждение репозитория и ветки; при ошибке — журнал сборки/запуска без секретов.

Проверить нужно:

- `/`, `/season`, `/profile`, `/progress`, `/programs`: загрузка и обновление прямых ссылок;
- все обложки, ролик и звук;
- почтовый вход, Google и выход;
- оба настоящих диалога ИИ и итог;
- сохранение с аккаунтом и чтение после обновления / на другом устройстве;
- баллы и права администратора;
- Telegram: подключение, фактическая доставка и отсутствие повторов;
- автодеплой безопасной правки из синхронизируемой ветки.

До успешных проверок рабочий сайт Lovable остаётся основным. Не заменяйте исправление ошибки отключением входа, проверок секретов или правил доступа.
